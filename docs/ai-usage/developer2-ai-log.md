## Session 1: Person module (repository + service)
**Date:** 2026-09-09  
**Tool:** Kimi Chat  
**Duration:** ~25 minutes  

### Purpose

Design the person module: `Person`, `Customer`, `Seller`,
`PersonRepository`, `PersonService`. This was the first module where I had
to build both persistence and service layer classes.

### Questions Asked

1. "How do I separate the persistence of customers and sellers in a single
   repository?"
2. "Should `PersonService` register sellers from the UI?"
3. "How do I initialize the three default sellers without violating SRP?"

### Feedback Received

- **One repository can handle two entity types** if the methods are
  `saveCustomers` / `loadCustomers` / `saveSellers` / `loadSellers` — no
  generic parameter needed.
- **Sellers should not be registered from the UI** — they are preloaded
  employees. So `PersonService` seeds them on first run.
- **The seeding should live in a separate class** (`SellerSeeder` or
  `DataSeeder`), not inside `PersonService`. This would keep `PersonService`
  focused on registration. (I did not apply this suggestion immediately —
  see Session 8 of this log.)

### Changes Applied

1. `PersonRepository` with `saveCustomers`, `loadCustomers`,
   `saveSellers`, `loadSellers`.
2. `PersonService` with `registerCustomer`, `listCustomers`, `listSellers`,
   `findCustomerById`, `findSellerById`.
3. **Seeded the three default sellers in the `PersonService` constructor**
   (I applied the suggestion in Session 8 instead of now — this was the SRP
   violation V-04 the R8 audit later flagged).

### Reflection

At the time, I thought seeding in the constructor was acceptable because it
was "just three sellers". In Session 8 I understood why it was not — the
service has two reasons to change.

## Session 2: CSV repository design
**Date:** 2026-09-11  
**Tool:** ChatGPT (DeepSeek)  
**Duration:** ~30 minutes  

### Purpose

Define the CSV format for all repositories. This was important because the
four modules would need to share the same conventions.

### Questions Asked

1. "What separator should I use — comma, semicolon, or pipe?"
2. "How do I store a list of IDs in a single field?"
3. "How do I distinguish between subtypes in a persisted file?"
4. "Should I escape semicolons in titles?"

### Feedback Received

- **Semicolon separator** for the main fields, because product titles can
  contain commas.
- **Pipe `|` as inner separator** for lists of IDs (e.g.
  `compatibleConsoles`, `productIds`).
- **Type discriminator as the first field** (e.g. `CONTROLLER`, `CABLE`,
  `MEMORY`, `PERCENTAGE`, `CATEGORY`, `BULK`, `BASIC`, `EXTENDED`).
- **Yes, escape semicolons** — but for R7 it was not done (the out-of-scope
  finding OF-04 in the SOLID audit).

### Changes Applied

1. All repositories use `SEPARATOR = ";"`.
2. `AccessoryRepository` uses `CONSOLE_LIST_JOINER = "|"`.
3. `SaleRepository`, `ReturnRepository`, `WarrantyRepository` use
   `PRODUCT_JOINER = "|"` for product IDs.
4. Every repository has a `type` discriminator as the first field.
5. **Did not implement escaping** — noted as a future improvement.

### Reflection

The CSV format was the most important decision of the whole project. Once
it was defined, all repositories were implementations of the same pattern.
I should have implemented escaping, but the assignment did not require it.

## Session 3: AccessoryService and AccessoryRepository
**Date:** 2026-09-14  
**Tool:** Kimi Chat  
**Duration:** ~25 minutes  

### Purpose

Implement the accessory persistence and service. `AccessoryRepository` from
the model I had designed with Developer 1, and `AccessoryService` with the
`registerController`, `registerCable`, `registerMemory` methods.

### Questions Asked

1. "How do I return the correct subtype from `fromCsvLine`?"
2. "Should `AccessoryService.findById` throw or return `null`?"
3. "How do I persist the `compatibleConsoles` list in CSV?"

### Feedback Received

- **`fromCsvLine` should use a `switch` on the type discriminator** and
  return the appropriate subclass. This is acceptable at the persistence
  boundary because the discriminator was written by us.
- **`findById` should throw `NoSuchElementException`** because a caller
  asking for a specific ID is expecting it to exist. `null` would hide bugs.
- **`compatibleConsoles` is stored as `|`-joined string** and parsed back
  with `split("\\|")`.

### Changes Applied

1. `AccessoryRepository.fromCsvLine` uses `switch (type)`.
2. `AccessoryService.findById` throws `NoSuchElementException`.
3. `AccessoryRepository.toCsvLine` / `fromCsvLine` handle `|` list encoding.

### Reflection

The `findById` decision was made in isolation. I did not know at the time
that `ProductService.findById` (Developer 1's class) returned `null` on
miss. That divergence is the ISP violation V-14 the R8 audit flagged.

## Session 4: PromotionService and WarrantyService
**Date:** 2026-09-17  
**Tool:** Kimi Chat  
**Duration:** ~30 minutes  

### Purpose

Implement the promotion and warranty services.

### Questions Asked

1. "Should `registerCategoryDiscount` validate the category?"
2. "Where does `findBestPromotionFor` belong — in the service or in the
   sale?"
3. "How do I assign warranties without overwriting the existing ones?"

### Feedback Received

- **Yes, validate the category**. But hardcoding the three values
  (`VIDEOGAME`, `CONSOLE`, `ACCESSORY`) is a violation of OCP. A `Category`
  enum would be better. (I applied the validation but not the enum — this
  became V-11 in R8.)
- **`findBestPromotionFor` belongs in `PromotionService`** — business rules
  belong to the service, not the entity.
- **Never use `List.of(warranty)`** when assigning a warranty — it replaces
  the existing list. Use `warrantyRepository.loadAll()` + `add` + `saveAll`.

### Changes Applied

1. `PromotionService.registerCategoryDiscount` validates against
   `VIDEOGAME`, `CONSOLE`, `ACCESSORY` (hardcoded — V-11).
2. `PromotionService.findBestPromotionFor(Sale)` iterates active promotions
   and returns the one with the highest discount.
3. `WarrantyService.assignBasicWarranty` and `assignExtendedWarranty` use
   `loadAll` + `add` + `saveAll`.
4. `WarrantyService.listActiveWarranties` and `listWarrantiesExpiringSoon`.

### Reflection

The `List.of` bug was a real runtime error — it overwrote the previous
warranties silently. The AI caught it during the review. I understood the
bug and applied the fix.

## Session 5: ReturnService and ReturnRepository
**Date:** 2026-09-19  
**Tool:** ChatGPT (DeepSeek)  
**Duration:** ~35 minutes  

### Purpose

Implement the return module — the last of the four modules. The most
complex because it interacts with sales, warranties, and inventory.

### Questions Asked

1. "Should `ReturnService` inject `WarrantyService` and `AccessoryService`?"
2. "How do I restore stock for accessories and products in a single loop?"
3. "Where should the monthly balance report live?"
4. "How do I avoid the orphaned-return problem when a sale is missing?"

### Feedback Received

- **Yes, inject both** `WarrantyService` (for A7 — warranty cancellation)
  and `AccessoryService` (for A4 — accessory stock restoration). This is
  the `instanceof` branching V-12 in R8.
- **Stock restoration uses `instanceof`**. This is a violation of
  Indirección (V-07 in GRASP). A façade would be cleaner, but for R7 the
  `instanceof` is acceptable.
- **Monthly balance belongs in `ReturnService`**. This is the SRP violation
  V-06 the R8 audit flagged.
- **Orphaned returns**: if the sale is missing, return `null` from
  `fromCsvLine`. Do not throw — this would break the whole load.

### Changes Applied

1. `ReturnService.registerReturn` calls `warrantyService.cancelWarranties`
   for consoles and `accessoryService.restoreStock` for accessories.
2. `ReturnRepository.fromCsvLine` returns `null` if the sale is not found.
3. `ReturnService.calculateMonthlySales`, `calculateMonthlyReturns`,
   `generateMonthlyBalance`.

### Reflection

The return module is where the four modules of R7 meet. The `instanceof`
branching was the only way to make it work at the time, but it is exactly
the kind of violation that GRASP and SOLID both flag (V-07 in GRASP,
V-12 in SOLID).

## Session 6: Integration error identification (service layer)
**Date:** 2026-09-27  
**Tool:** ChatGPT (DeepSeek)  
**Duration:** ~45 minutes  

### Purpose

Final integration review. My role was to verify the service and persistence
layers.

### Questions Asked

1. "Does my persistence layer comply with the required CSV format?"
2. "Are there compilation errors in my services?"
3. "Do my repositories properly resolve cross-references?"
4. "Is `ReturnService.registerReturn` correctly delegating?"

### Issues Identified

**Persistence layer:**
- Some repositories used `.dat` serialization instead of CSV.
- `saveAll` in several repositories received a single object instead of a
  `List`.
- `loadAll` was `private` and returned `void` in some repositories.
- Missing `type` discriminator in `PromotionRepository` and
  `WarrantyRepository`.
- Missing `findById` in `SaleRepository` and `WarrantyRepository`.
- `SaleRepository` called a constructor of `Sale` that did not exist.
- `WarrantyRepository` and `ReturnRepository` had circular dependencies.

**Service layer:**
- `ProductService` used old methods `load()` / `save()` that no longer
  existed.
- `PromotionService.registerPercentageDiscount` received a generic
  `Promotion` instead of specific parameters.
- `SaleService.registerSale` had inverted stock validation logic.
- `SaleService` used old method `savesales` instead of `saveAll(List)`.
- `WarrantyService.assignBasicWarranty` used `List.of(warranty)` which
  overwrote existing warranties.
- `ReturnService` did not exist.

### Actions Taken by Me

1. Migrated `.dat` repositories to CSV with type discriminators.
2. Fixed `saveAll` and `loadAll` signatures in all repositories.
3. Injected dependencies in `SaleRepository`, `WarrantyRepository`, and
   `ReturnRepository`.
4. Corrected `PromotionService`, `WarrantyService`.
5. Created `ReturnService`.
6. Reported `SaleService` and `ProductService` issues to their owners
   (Leader and Developer 1 respectively).

### Reflection

This session confirmed that the persistence layer is the most fragile part of
the system because it crosses module boundaries. The circular dependency in
`WarrantyRepository` (fixed later in A2) was the hardest bug.

## Session 8: SOLID audit (service and persistence classes)
**Date:** 2026-10-21  
**Tool:** ChatGPT (DeepSeek)  
**Duration:** ~40 minutes  

### Purpose

Audit my service and persistence classes against SRP, OCP, LSP, ISP, DIP for
R8.

### Questions Asked

1. "Does `PersonService` seeding sellers violate SRP?"
2. "Does `ReturnService` including monthly balance violate SRP?"
3. "Does `PromotionService.registerCategoryDiscount` violate OCP?"
4. "How do I unify `ProductService.findById` (returns `null`) with
   `AccessoryService.findById` (throws) without breaking the code?"
5. "What is the best way to introduce `InventoryService` respecting DIP?"

### Findings

- **`PersonService` seeding sellers**: SRP violation (V-04). Fix:
  `SellerSeeder`.
- **`ReturnService` including monthly balance**: SRP violation (V-06). Fix:
  `MonthlyBalanceService`.
- **`PromotionService.registerCategoryDiscount`**: OCP violation (V-11).
  Fix: `Category` enum.
- **Divergent `findById` contracts**: ISP violation (V-14). Fix:
  `InventoryService.findById → Optional`.
- **`ReturnService` with 5 concrete dependencies**: DIP violation (V-16).
  Fix: `InventoryService` + interfaces.
- **`AccessoryService`, `PromotionService`, `WarrantyService`,
  `PersonService` depend on concrete repositories**: DIP violation (V-17c).
  Fix: `I*Repository` interfaces.
- **`WarrantyRepository` and `ReturnRepository` depend on 3 concrete
  repositories**: DIP violation (V-18). Fix: `ISaleLookup`,
  `IProductLookup`.

### Changes Applied

1. Wrote my `docs/solid-audit/developer2-audit.md` covering V-04, V-06,
   V-10b, V-11, V-14, V-16, V-17c, V-18.
2. Confirmed border findings with Dev 1 (V-10b, V-14) and Leader (V-16,
   V-18).
3. Designed the `InventoryService` contract with the Leader:
   - `Optional<Product> findById(String)`
   - `boolean hasEnoughStock(String, int)`
   - `boolean reduceStock(String, int)`
   - `boolean restoreStock(String, int)`
4. Agreed the split: I create `InventoryService` (first PR), Leader updates
   the callers (second PR).

### Reflection

The `InventoryService` is the single most impactful change of R8: it
resolves V-05, V-08, V-12, V-13, V-14, V-15, V-16 all at once. Designing it
was the hardest part; the implementation is straightforward.

## Key Learnings

1. **Semicolon as CSV separator** avoids conflict with commas in titles.
   Pipe `|` as inner separator for lists.
2. **Type discriminator** must be the first field for polymorphic
   deserialization.
3. **`findById` should have a single contract** across the codebase.
   Divergence between `null` and `throw` is a design smell.
4. **Persist IDs, not objects**. `WarrantyRepository` and `ReturnRepository`
   store IDs and resolve references.
5. **The constructor is not the place for seeding**. Business initialization
   belongs in a dedicated seeder class, called from `Main`.
6. **Monthly reports do not belong in the return service**. Separate
   concerns, separate classes.
7. **`InventoryService` is the façade that R8 needs**. It unifies two
   divergent stock services into a single polymorphic contract.
