## Session 1: Sale and SaleService — initial design review
**Date:** 2026-09-08  
**Tool:** Kimi Chat  
**Duration:** ~30 minutes  

### Purpose

Review the initial design of `Sale` and `SaleService` before the modules were
integrated. I wanted to check whether the class attributes and the method
signature were coherent with the base system from Workshop 1.

### Questions Asked

1. "Does my `Sale` class have the right attributes to support discounts and
   extended warranties later?"
2. "Is `SaleService.registerSale(Customer, Seller, List<Product>)` a good
   signature, or should the sale be constructed outside the service?"
3. "What is the difference between composition and aggregation for `Sale`
   holding `Customer`, `Seller`, and `List<Product>`?"

### Issues Identified

- **Missing attributes for future integration.** `Sale` was missing
  `appliedPromotionName` and `discountAmount`. Without them, the promotion
  module would have to store the discount elsewhere, splitting the source of
  truth.
- **`extendedWarrantyCost`** was also missing. I added it before the warranty
  module existed, anticipating that extended warranties add a cost to the
  final total.
- **`getProducts()` returning the internal list** would let callers mutate
  the sale. Defensive copying was recommended.

### Changes Applied

1. Added `appliedPromotionName`, `discountAmount`, and
   `extendedWarrantyCost` to `Sale`.
2. Made `getProducts()` return `new ArrayList<>(products)`.
3. Added `calculatePrice()` and `calculateTotal()` as domain methods
   (`calculateTotal = calculatePrice − discountAmount + extendedWarrantyCost`).
4. Documented `SaleService.registerSale` as the **single entry point** for
   sale creation — the service, not the caller, decides the sale id.

### Reflection

Kimi helped me separate the "sale state" from the "sale creation flow". I
understood each suggestion and applied the changes myself. The signature
review saved me from having to refactor `SaleService` twice.

## Session 2: ConsoleMenu and Main structure
**Date:** 2026-09-10  
**Tool:** ChatGPT (DeepSeek)  
**Duration:** ~25 minutes  

### Purpose

Review the structure of `ConsoleMenu` and `Main` before adding the four new
submenus (accessories, promotions, warranties, returns). The goal was to make
sure the dependency wiring in `Main` would scale to seven menus.

### Questions Asked

1. "Should `Main` construct all services and pass them to `ConsoleMenu`, or
   should `ConsoleMenu` build them?"
2. "Is it acceptable for `ConsoleMenu` to depend on 7 service classes?"
3. "How do I avoid a circular dependency between `SaleService` and
   `WarrantyService` in `Main`?"

### Feedback Received

- **`Main` must be the composition root.** Building services inside
  `ConsoleMenu` would violate the layered architecture: the UI must not
  know about persistence.
- **Seven service dependencies in `ConsoleMenu` is acceptable** because
  `ConsoleMenu` is a dispatcher — it does not use them itself, it only passes
  them to submenus.
- **Circular dependencies in `Main` are resolved by order of construction.**
  Build repositories first, then services in dependency order, then the menus.

### Changes Applied

1. `Main` builds all repositories, then all services, then `ConsoleMenu`.
2. `ConsoleMenu` receives all 7 services in its constructor and passes them
   to each submenu.
3. Each submenu receives only the services it actually uses (e.g.
   `AccessoryMenu` only takes `AccessoryService`, `ProductService`, and
   `Scanner`).

### Reflection

The key insight was that the "composition root" is a single place — `Main`.
Once that was clear, the dependency graph wrote itself. I did not know the
term before this session.

## Session 3: Multi-module integration design
**Date:** 2026-09-15  
**Tool:** Kimi Chat  
**Duration:** ~40 minutes  

### Purpose

Design the integration plan for R7: how the 4 modules (accessories,
promotions, warranties, returns) interact with the base system, and which
integration adjustments (A1–A7) are needed.

### Questions Asked

1. "If a sale contains a console and the seller wants to add an extended
   warranty, where should that decision be made?"
2. "Should `SaleService` know about `WarrantyService`, or should the sale
   be created first and then warranties added by the caller?"
3. "What breaks if `CategoryDiscount` does not know about the `ACCESSORY`
   category?"
4. "How do I avoid `SaleService` becoming a god class once all four modules
   are integrated?"

### Feedback Received

- **Extended warranty decision belongs in `SaleService`**, not in the UI.
  The UI should only ask y/n; the service decides the eligibility and
  generates the warranty.
- **`SaleService` will become a coordinator**, which is acceptable *if*
  the responsibilities it delegates are single-purpose. It should not compute
  warranty cost itself (that belongs to `Warranty.getAdditionalCost`).
- **`CategoryDiscount` must recognize the three categories** —
  `VIDEOGAME`, `CONSOLE`, `ACCESSORY` — or accessory promotions silently
  compute zero discount.

### Changes Applied

1. Added `SaleService.registerSale(..., List<String> extendedWarrantyIds)`
   as the single entry point that orchestrates:
   subtotal → best promotion → basic warranties → extended warranties →
   final total → inventory → persist.
2. Registered A1 (accessory category discount) as a planned feature branch.
3. Registered A3 (unified sale flow) as the target behavior — the actual
   code change came in Session 5.
4. Registered A2 (circular dependency) as a known issue to be resolved in
   Session 4.

### Reflection

This session was where I first realized the four modules could not be
integrated "one by one" — they had to be designed together. The order of
operations in `registerSale` is not arbitrary; each step depends on the
previous one.

## Session 4: A2 — Resolving the circular dependency in the warranty module
**Date:** 2026-09-20  
**Tool:** Kimi Chat  
**Duration:** ~30 minutes  

### Purpose

The build was failing because `SaleService → WarrantyService →
WarrantyRepository → SaleService` created a compile-time cycle.
`WarrantyRepository` needed to resolve `Sale` references during loading, and
my first version made it depend on `SaleService`.

### Questions Asked

1. "How do I persist a `Warranty` without a reference to `SaleService`?"
2. "Is it acceptable for a repository to depend on another repository?"
3. "What is the recommended way to resolve cross-repository references in a
   layered architecture?"

### Issues Identified

- **The cycle was real, not just a design smell.** Java would not compile
  because the classes depended on each other at the type level.
- **The fix is to persist IDs, not objects.** `WarrantyRepository` should
  store `saleId` and `productId` as strings, not `Sale` and `Product`
  references.
- **Cross-repository resolution is acceptable** at the persistence layer, as
  long as it stays in the same layer (persistence → persistence) and does
  not reach up to services.

### Changes Applied

1. `WarrantyRepository` now persists `type;id;productId;saleId;startDate;endDate`.
2. `WarrantyRepository` depends on `SaleRepository` and `ProductRepository`
   (both persistence-layer classes), **not** on `SaleService`.
3. `WarrantyService` is responsible for resolving references if needed.
4. `Main` builds repositories before services, breaking the cycle at
   construction time.

### Reflection

This was the first time I understood why "persistence depends on persistence"
is fine, but "persistence depends on service" is not. The A2 fix also
incidentally improved a DIP violation (see the R8 SOLID audit, V-18), which I
only noticed much later.

## Session 5: A3 — Unified sale registration flow
**Date:** 2026-09-22  
**Tool:** ChatGPT (DeepSeek)  
**Duration:** ~35 minutes  

### Purpose

Three R7 requirements (accessory stock, promotion application, warranty
assignment) modified `SaleService.registerSale` independently during
integration. The order of operations became ambiguous and I needed to
establish a definitive order.

### Questions Asked

1. "What is the correct order for: subtotal, promotion, warranties, final
   total, inventory, persist?"
2. "Should inventory be updated before or after persistence?"
3. "Where should the extended warranty cost be added to the sale?"

### Feedback Received

- **Correct order** (recommended by the AI and confirmed by me):
  1. Validate at least one item.
  2. Validate stock (products and accessories).
  3. Create the sale and calculate subtotal.
  4. Query the best promotion and register the discount.
  5. Generate basic warranties for consoles, and extended warranties when
     requested.
  6. Calculate final total: subtotal − discount + extended warranty cost.
  7. Update inventory.
  8. Persist the sale and warranties.
- **Inventory before persistence**: if persistence fails, we can rollback
  more easily. In our case neither happens, but the order is defensive.
- **Extended warranty cost belongs to the sale** (as `extendedWarrantyCost`)
  so that `calculateTotal()` and `generateReceipt()` see the same value.

### Changes Applied

1. Rewrote `SaleService.registerSale` following the exact 8-step order
   above.
2. Added `sale.setExtendedWarrantyCost(warrantyCost)` after the warranty
   assignment loop.
3. Confirmed that `Sale.generateReceipt()` shows the 5 relevant values:
   subtotal, promotion name, discount, extended warranty cost, final total.

### Reflection

This was the most important integration session. The order of operations
affects the result, and there was no "obviously correct" order before the
session. The AI's suggestion matched what the R7 document describes in A3.
I applied the code changes myself and verified each step.

## Session 6: Integration error identification (leader's perspective)
**Date:** 2026-09-27  
**Tool:** ChatGPT (DeepSeek)  
**Duration:** ~90 minutes  

### Purpose

Final integration review before the R7 submission. My role in this session
was to coordinate the cross-module verification and confirm that the three
integrators' work fit together: `SaleService`, `ReturnService`, and the
warranty/return interaction.

### Questions Asked

1. "Does `SaleService.registerSale` follow the unified flow from A3?"
2. "Does `ReturnService.registerReturn` correctly call `cancelWarranties`
   for returned consoles?"
3. "Does `Return.calculateRefundAmount` apply the proportional discount
   from A5?"
4. "Does `ReturnMenu.showMonthlyBalance` display the three values from A6?"
5. "Does the `Main` class build all services in the correct order?"

### Issues Identified

**In `SaleService`:**
- `SaleService.registerSale` accepted `(Sale)` instead of `(Customer,
  Seller, List<Product>, List<String>)`. The old signature was from before
  the warranty module existed.
- `SaleService` was calling `sales.add(sale); saveData()` instead of
  `saleRepository.loadAll()` + `add` + `saveAll`.
- Stock validation was inverted: it threw when stock was sufficient.

**In `ReturnService`:**
- `ReturnService.registerReturn` did not call
  `warrantyService.cancelWarranties` for returned consoles (A7 was missing).
- `ReturnService` did not inject `AccessoryService`, so returned accessories
  had no stock restoration (A4 was missing).

**In `Return`:**
- `calculateRefundAmount` summed list prices, over-refunding discounted
  sales (A5 was missing).
- `generateReturnReceipt` did not show the discount breakdown.

**In `Main`:**
- `Main` constructed `SaleService` with the wrong signature.
- `Main` did not construct `ReturnService`.

**In `ReturnMenu`:**
- `showMonthlyBalance` printed only the net balance, not the three values
  (A6 was missing).

### Actions Taken by Me (Technical Lead)

1. Rewrote `SaleService.registerSale` with the correct signature and order.
2. Rewrote `SaleService` to use `saleRepository.loadAll()` +
   `saveAll(sales)`.
3. Fixed `ReturnService.registerReturn` to call `cancelWarranties` for
   consoles and to delegate to `AccessoryService.restoreStock` for
   accessories.
4. Updated `Return.calculateRefundAmount` and `generateReturnReceipt`.
5. Fixed `Main` construction order.
6. Updated `ReturnMenu.showMonthlyBalance` to print the three values.

### Reflection

The AI did not provide code. It pointed at where the errors were, why each
was a problem, and what the correct behavior should be. I located each error
in the code, understood the cause, and applied the corrections myself. As
Technical Lead, this session was the most valuable because it forced me to
trace the four modules end-to-end.

## Session 7: GRASP audit coordination (R7 close)
**Date:** 2026-10-14  
**Tool:** Kimi Chat  
**Duration:** ~45 minutes  

### Purpose

Coordinate the R7 GRASP audit. My role was not to audit every class (the
team split the coverage), but to design the audit structure, resolve border
violations, and consolidate.

### Questions Asked

1. "How do I structure a consolidated audit so it does not repeat what each
   individual audit says?"
2. "What makes a veredict (violation / correct / not applicable) defensible
   without being subjective?"
3. "How do I handle a violation that two integrantes report independently?"

### Feedback Received

- **Three veredicts with objective criteria**: violation (positive evidence
  of the antipattern in code), correct (evidence of the pattern), not
  applicable (the pattern does not apply to that class).
- **Minimum evidence per veredict**: class, method, exact fragment,
  explanation, and consequence. Without all five, the finding is not
  admissible.
- **Border violations**: register as a single consolidated violation with a
  shared ID, split the correction across integrantes, define the order of
  the two PRs.

### Changes Applied

1. Designed the coverage table so each class is audited by exactly one
   integrante (its owner).
2. Established the "minimum evidence" rule in the consolidated audit's
   opening section.
3. Registered three border violations: V-04/V-07 (`InventoryService`),
   V-05 (`Sale.calculateWarrantyCost`), V-02 (Polimorfismo in `SaleService`
   and `Product` hierarchy).
4. Wrote `docs/grasp-audit/consolidated-audit.md` with the final list.

### Reflection

The audit structure is more important than the number of findings. A
well-structured audit with 8 defensible violations is better than a long
list of weak ones. I wrote the consolidated audit myself, referencing the
individual audits.

## Session 8: SOLID audit coordination (R8)
**Date:** 2026-10-21  
**Tool:** ChatGPT (DeepSeek)  
**Duration:** ~60 minutes  

### Purpose

Coordinate the R8 SOLID audit. Same structure as the R7 GRASP audit but
applied to the five SOLID principles (with LSP audited per class in the
individual reports, not in `solid-analysis.md`).

### Questions Asked

1. "Which of my classes (`Sale`, `SaleService`, `SaleMenu`, `Main`) violate
   SRP, OCP, LSP, ISP, DIP?"
2. "How do I relate the SOLID findings to the R7 GRASP audit without
   copying `grasp-analysis.md`?"
3. "How do I structure the border findings so `InventoryService` resolves
   seven violations at once without becoming a god object?"
4. "What is the minimum evidence for a SOLID violation, and how is it
   different from GRASP?"

### Feedback Received

- **R8 Q3 is not LSP — it is the SOLID ↔ GRASP relationship.** Two cases
  are required: one where a SOLID violation survived a GRASP fix (Case A),
  one where a GRASP fix incidentally fixed a SOLID (Case B).
- **`InventoryService` resolves seven violations across four principles**
  (SRP V-05, LSP V-12, ISP V-13, DIP V-15/V-16). This is not a god object
  because it has a single responsibility (stock operations) and its contract
  is narrow (4 methods).
- **Minimum evidence for SOLID** is the same as GRASP (class, method,
  fragment, explanation, consequence) plus the **refactor direction**
  (proposed solution).

### Changes Applied

1. Designed `solid-analysis.md` with 5 questions (SRP, OCP, SOLID↔GRASP,
   ISP, DIP) — LSP moved to individual audits.
2. Wrote Q3 with the two required cases: V-01 (SRP that A3 worsened) and
   V-18 (DIP that A2 partially fixed).
3. Wrote my own `docs/solid-audit/leader-audit.md` covering 8 violations
   (V-01, V-05, V-07, V-08, V-09, V-12, V-13, V-15).
4. Consolidated the three audits into `docs/solid-audit/consolidated-audit.md`
   with 18 violations and 3 border findings (B-1, B-2, B-3).
5. Split the `InventoryService` correction: Developer 2 creates the class,
   I update the callers in `SaleService`, `ReturnService`, `SaleMenu`, and
   `Main`.

### Reflection

The SOLID audit is structurally similar to the GRASP audit but demands a
proposed solution per violation, not just a consequence. That made it
heavier: 18 violations each require a fix direction. I did not copy code from
AI; I designed the fix directions and the split of work myself.

## Key Learnings

1. **Composition root**: `Main` builds everything, once. No other class
   instantiates services.
2. **Order of operations matters**: in `registerSale`, subtotal → promotion
   → warranties → total → inventory → persist is not arbitrary.
3. **Persist IDs, not objects**: `WarrantyRepository` stores `saleId` and
   `productId` as strings; resolution happens at the service layer.
4. **Audit structure over finding count**: a defensible audit is more
   valuable than a long one.
5. **Border violations**: when two integrantes report the same violation
   from opposite sides, register it once with a shared ID and split the fix.
6. **A refactor can make things worse**: A3 extended `Sale.generateReceipt`,
   which improved GRASP cohesion but aggravated the SRP violation (V-01).
7. **A refactor can fix things in passing**: A2 reduced the DIP violation in
   `WarrantyRepository` (V-18) without intending to.
